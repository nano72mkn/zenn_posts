どうも、[nano72mkn](https://x.com/nano72mkn)です。

前回[Claude Codeをはじめて触るエンジニアのためのざっくり入門](https://zenn.dev/stafes_blog/articles/nano72mkn-claude-code-intro)という記事を書いたんですが、その中で「コンテキストが膨らみすぎるとClaudeも混乱するので、こまめに切り替えるのがコツです」みたいなことをサラッと書きました。

書いた後に「いやそもそもコンテキストって何ぞや、というところから話したほうがよかったな」と思ったので、改めてまとめておきます。

Claude Codeに限らず、ChatGPTでもCursorでも、最近のAIツールを使う上で**コンテキスト**という言葉は避けて通れないです。ここを掴んでおくと「なんで急に変なこと言い出した?」「なんでさっき言ったこと忘れてるの?」みたいなモヤモヤがスッと腑に落ちると思います。

今回もサクッと読める感じを目指します。

## コンテキストって何?

ざっくり言うと、**Claudeが今この瞬間に「見えている」ものすべて**です。

もう少し具体的に言うと、

- これまでのあなたとの会話の履歴
- Claudeが読んだファイルの中身
- 実行したコマンドの結果
- `CLAUDE.md` などの設定ファイル
- システムプロンプト (Anthropicが裏で渡している基本ルール)

これらを全部ひっくるめて「コンテキスト」と呼びます。

イメージとしては、**Claudeの作業机の上**みたいなものです。机の上に資料を広げながら作業している感じ。机が広ければ広いほどたくさん資料を置けるし、関係ない資料が散らかってると目当てのものが見つけづらくなる。そんな感覚で大丈夫です。

## なぜコンテキストが大事なのか

LLM (Claudeの中身) には、**学習時点までの知識**しかありません。
あなたのプロジェクトのことも、今日あなたが何をしていたかも、当然知らないわけです。

なので、AIに何かをやってもらうときは「**今この作業に必要な情報を、その場で渡してあげる**」必要があります。これがコンテキストです。

逆に言うと、**コンテキストに入っていない情報については、Claudeは何も知らない**ということ。

```
> このバグを直して
```

って言われても、Claudeから見ると「どのバグ?」となります。
コードを読んだり、エラーログを見たり、過去の会話を参照したり…そうやってコンテキストを集めて、はじめて作業ができる、という構造です。

## コンテキストには上限がある

ここが結構大事なポイントです。

コンテキストには**ウィンドウ**と呼ばれる上限があります。これは「机の広さ」みたいなもので、無限に何でも置けるわけじゃないです。

Claude Code (Claude Opus / Sonnet) の場合、けっこう広めの机が用意されていて、長めの会話やそこそこ大きいリポジトリも乗ります (この上限はモデルや設定によって変わります。標準だと20万トークン、環境によっては100万トークンまで使えたりします)。ただ、

- 大量のファイルを読ませる
- ログを丸ごと貼り付ける
- 長時間ずっと同じセッションで作業する

みたいなことをしていると、知らない間に机が資料で埋まってきます。

埋まってくるとどうなるか:

- **応答が遅くなる** (毎回大量の情報を読み直すため)
- **昔の話を忘れる** (古い情報から押し出される)
- **指示が通りにくくなる** (重要な指示が大量の情報の中で埋もれる)
- **お金がかかる** (APIの場合、コンテキストが大きいほどコストも上がる)

なんとなく「最近Claudeの調子悪いな…」と感じるときは、だいたいコンテキストが膨らみすぎてることが多いです。

### 「上限まで余裕があるから大丈夫」とは限らない

ここで一つ大事な注意点があります。

「上限が100万トークンもあるなら、埋まるまでガンガン詰め込んでOKでしょ」と思いがちなんですが、**実は上限に達するずっと手前から、性能はじわじわ落ちていきます**。

Chromaが出している [Context Rot](https://www.trychroma.com/research/context-rot) という研究が分かりやすいです。ざっくり言うと、

- 入力が長くなるほど、LLMが**情報を正確に思い出す能力は低下していく**
- しかもその劣化は**均一じゃない** (急にガクッと落ちることもある)
- 関係ない情報 (ノイズ) が混ざっていると、さらに精度が落ちる
- 「何の情報があるか」より「**どう提示されているか**」のほうが性能を左右する

という結果が報告されています。これがいわゆる **Context Rot (コンテキストの腐敗)** と呼ばれる現象です。

机の比喩で言うと、**机がデカくても、資料を山積みにすればするほど目当ての一枚を見つけ損なう**ということ。「まだ空きがあるから」と詰め込み続けると、いつの間にか精度が落ちている、というのはよくある罠です。

だからこそ、上限ギリギリまで使うのではなく、**こまめに整理して『関係あるものだけ机に乗っている』状態を保つ**のが効いてきます。

## `/context` で散らかり具合を見る

「じゃあ今どれくらい机が埋まってるの?」を確認できるのが **`/context`** コマンドです。

セッション中に `/context` と打つと、今のコンテキストの内訳がビジュアルで表示されます。

![/context の実行結果](/images/nano72mkn-context-intro/context.png)

ブロックの一つひとつがコンテキストの使用量を表していて、何にどれくらい使われているかが色分けで見られます。

- **System prompt / System tools** — Claude Codeが裏で使っている基本の枠 (ここは固定でかかる分)
- **Memory files** — `CLAUDE.md` などの設定ファイル
- **Skills** — 利用可能なSkillの説明 (※名前と説明だけ。後述します)
- **Messages** — あなたとの会話履歴
- **Free space** — まだ空いてる机のスペース

この画像だと `1m` (100万トークン) の机に対してまだ `4%` しか使っていないので、めちゃくちゃ余裕がある状態です (前述のとおり上限は環境によって変わるので、自分の画面の数字と違っても気にしないでください)。

逆に、ガッツリ作業を続けるとこうなります。

![コンテキストがたくさん使われている状態](/images/nano72mkn-context-intro/context-full.png)

こちらは `76%` まで埋まっていて、内訳を見ると **Messages が 73.8% (約74万トークン)** とほとんどを占めています。ここまで来ると机はかなり手狭で、Free spaceも残り `22.6%`。「最近応答が遅いな」「指示が通りにくいな」と感じはじめるのはだいたいこのあたりです。

長時間作業していて「重くなってきたな」と感じたら、`/context` で **Messages の割合がどれくらい膨らんでいるか**を見てみるといいです。Free spaceが残りわずかになっていたら、`/clear` や `/compact` の出番、という判断ができます。

ちなみに **MCP tools** については、少し前まで「繋いだサーバーのツール定義が全部コンテキストに乗る」状態で、MCPをたくさん繋ぐと机を圧迫する原因になっていました。

今は **必要なときだけツールを読み込む仕組み (Tool Search)** が入っていて、繋いでいるだけでは能動的なコンテキストをほとんど食わなくなっています。実際、上の画像でもMCPツールは「on-demand (必要時に読み込み)」扱いになっていて、使用量のカウントから外れています。

なので昔ほど神経質にならなくてよくなったんですが、お使いのバージョンや設定によってはまだ全部乗ることもあるので、「最近MCPいっぱい繋いだな」というときは `/context` で確認してみるといいです。

## コンテキストを管理する基本テクニック

ここからは実践編です。Claude Codeで使えるテクニックを並べていきます。

### `/clear` でリセットする

一番強くて簡単な方法。**話題が変わったら `/clear`**、これだけ覚えておけばまず困らないです。

```
タスクA (バグ修正) を終えた
→ /clear
→ タスクB (新機能の実装) を始める
```

「これと関係ないけどついでにこれもお願い」みたいな投げ方を続けていると、机がどんどん散らかります。話題ごとにキレイな机で始めるのが基本です。

### `/compact` で圧縮する

「今のセッションは続けたいけど、コンテキストが膨らんできた」というときに使います。
これまでのやり取りを**要約して圧縮**してくれるイメージです。

長時間の実装作業の途中で「もうちょっと続けたいけど重くなってきたな」と感じたら、`/compact` を挟むと机が片付きます。

ただし圧縮なので、細かい情報はある程度落ちます。「あの細かいニュアンスは覚えていてほしい」という場面では、思い切って `/clear` してから必要な情報だけ渡し直すほうが結果的に早かったりします。

### `/btw` で寄り道する

前回の記事でも紹介した `/btw` (by the way)。
これも実は**コンテキスト管理のためのコマンド**です。

```
/btw このコマンドのオプションって何があったっけ?
```

`/btw` で質問すると、その質問と回答は**メインの会話履歴に残らない**ので、長い作業の途中で寄り道してもコンテキストが汚れません。

「ちょっとした確認」のために `/clear` するのはもったいないし、かと言って雑に質問するとコンテキストが膨らむ…そんなときの折衷案として便利です。

### `CLAUDE.md` で「最初から知ってる」状態を作る

これは攻めの戦略です。

`CLAUDE.md` に書いたことは、**毎セッションの最初から自動でコンテキストに入ります**。

- テストコマンド (`bun test`)
- コミットルール
- プロジェクトの構成
- やってほしくないこと (例: `--no-verify`は使わない)

こういう「毎回伝えてること」を `CLAUDE.md` にまとめておけば、毎回口頭で伝える必要がなくなる = その分のコンテキストが節約できます。

「毎回同じこと言ってるな」と思ったら、それは `CLAUDE.md` に書くサインです。

## コンテキストとうまく付き合うコツ

コマンドの話だけだとちょっと味気ないので、運用面のコツも置いておきます。

### タスクは小さく区切る

「全部いっぺんに」より「1つずつ」のほうが結果的に早いし、精度も高いです。
1タスク終わったら `/clear`、というリズムを意識すると、変な脱線が起きにくくなります。

### 関係ないファイルを読ませない

「とりあえずプロジェクト全体を読んで」みたいなお願いは、ロマンはあるんですが机が一瞬で埋まります。

Claude Codeは賢いので、必要なファイルは自分で探してきてくれます。
こちらから渡すときは、「このファイルだけ見て」くらいピンポイントなほうがうまくいきます。

### 大きい出力はファイルに逃がす

ログ、長文の調査結果、生成された大量のJSON…そういうものを会話の中で受け取ると、机がすぐ埋まります。

```
> 調査結果を ./tmp/report.md に書いて
```

みたいに、**ファイルに書いてもらう**と、必要なときだけ読み返せばよくなって、コンテキストにも優しいです。

### Plan modeを活用する

`Shift + Tab` で切り替えられる **Plan mode** は、いきなり実装に入らずに計画だけ立ててくれるモードです。

「あれ?なんか違う方向に進んでない?」と気づいたときには、すでにファイルがたくさん書き換わってコンテキストも汚れている、というのがよくあるやらかしです。

最初にPlanを立ててもらって、方向性のすり合わせをしてから動いてもらうと、無駄な試行錯誤が減ってコンテキストの消費もぐっと抑えられます。

## Skillsは「必要なときだけ」読み込まれる

前回の記事で紹介した**Skills** (`/<name>` で呼び出せる自作コマンド) も、実はコンテキストの面でよく考えられた仕組みになっています。

ポイントは、**Skillの中身は、呼び出されるまでコンテキストに入らない**ということです。

`.claude/skills/` にSkillをいくつ置いても、最初から全部の中身が机に広げられるわけではありません。Claudeが最初に見ているのは「どんなSkillがあるか」という**名前と一行説明だけ**です。

```markdown
---
description: 変更内容をconventional commits形式でコミットする
---

(↑この説明文だけが最初に見えている。本文は呼ばれるまで読み込まれない)
```

そして `/commit` のように実際に呼び出されたときに、はじめてそのSkillの本文がコンテキストに読み込まれます。

これがなぜ嬉しいかというと、

- **手順書を大量に用意しても机が埋まらない** — 使うときだけ広げられるので
- **長い手順を毎回プロンプトに貼らなくていい** — Skillに書いておけば呼ぶだけ
- **必要な知識を必要なときだけ渡せる** — まさにコンテキスト管理の理想形

「毎回コピペしてる長いプロンプト」をSkillにすると、プロンプトを打つ手間が減るだけじゃなく、**普段はコンテキストを消費せず、使うときだけ読み込まれる**という二重のおいしさがあります。

長めの手順やお作法は、会話で毎回伝えるよりSkillに逃がしておくほうが、机をキレイに保てるというわけです。

## サブエージェントという選択肢

もう一歩進んだ話として、**サブエージェント (Subagents)** という機能があります。

簡単に言うと、**自分の机とは別の机を持った、もう一人のClaude**を呼び出して作業させる仕組みです。

```
> このリポジトリのどこでAPIキーを使ってるか調べて
```

こういう「ガッツリ調査が必要なやつ」をメインの会話でやらせると、ファイルを大量に読んで机が一瞬で埋まります。

そこでサブエージェントの出番。サブエージェント側で調査をしてもらって、**最終的な結論だけ**メインの机に持ち帰ってもらう、ということができます。途中で読んだ大量のファイルは、サブエージェントの机の上で完結するので、メインの机はキレイなまま。

「重い調査タスク」「大量のファイル探索」みたいなものを任せるときに、特にコンテキスト節約の面で効きます。

詳しい使い方は[公式ドキュメント](https://code.claude.com/docs/ja/sub-agents)を見てください。

## コンテキストエンジニアリングという言葉

最近、**コンテキストエンジニアリング (Context Engineering)** という言葉を見かけることが増えました。

要は「AIに何を見せて、何を見せないか」を意図的に設計するスキルのことです。

プロンプトエンジニアリングが「**どう聞くか**」だとすると、コンテキストエンジニアリングは「**何を渡すか / 渡さないか**」の話。

- 必要な情報だけを、必要なタイミングで渡す
- 不要になった情報はリセットする
- 繰り返し使う情報はあらかじめ仕込んでおく
- 重い情報は外に逃がして、必要なときだけ参照する

…と書くと大げさですが、ここまで紹介してきた `/clear` も `CLAUDE.md` もサブエージェントも、全部これの一部です。

「AIに上手く仕事をさせる人」と「なんかいまいち噛み合わない人」の差は、プロンプトの文面より、こういうコンテキスト設計の差から来ていることが多い気がします。

## さいごに

まとめると:

1. コンテキスト = Claudeが今見えているもの全部
2. 上限があるので、無限には積めない
3. 散らかってくると精度も速度も落ちる
4. 散らかり具合は `/context` で確認できる
5. `/clear`, `/compact`, `/btw`, `CLAUDE.md`, Skills で整理する
6. 重いタスクはサブエージェントに逃がす

最初のうちは「机が散らかってきたら片付ける」くらいの感覚で十分です。
慣れてくると、**最初から散らかさない渡し方**ができるようになってきて、これがいわゆるコンテキストエンジニアリングへの第一歩になります。

Claude Codeに限らず、ChatGPTでもCursorでもGeminiでも、考え方はだいたい同じです。
一度この感覚を掴んでおくと、別のAIツールに乗り換えても応用が効くので、覚えておいて損はないはずです。

それでは、よきAIライフを!
